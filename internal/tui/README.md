# TUI

The terminal UI is three packages: a pure reducer (`state`), a pure renderer (`render`), and a thin shell (`bubble`) that does all I/O. Two more serve the shell: `composer`, the prompt input it owns, and `term`, uah's own terminal layer, which runs it: the event loop, the line renderer, and the terminal's modes. uah used Bubble Tea v2 until 1.8.4.

<!-- memoria:export id="summary" -->
The TUI is a pure reducer from session events and user intents to state and effects, a pure renderer from state to screen lines, and a thin shell on uah's own terminal layer that turns keys into intents and runs the effects against the session. As in Codex, enter while the agent works gives it the message after its running tool calls and tab queues it for the end of the run. Esc esc interrupts, and ctrl+v pastes an image.

## Packages

| Package | Does | Must not |
| --- | --- | --- |
| `state` | Holds `State` and `Reduce(state, event or intent) (State, []Effect)`. Knows the transcript, the queue, pending approvals, the picker, the menu, and the slash commands | Import `term` or lipgloss, or do I/O. Effects are values |
| `render` | Draws `State` into lines with lipgloss: `Screen(state, cache, frame)` returns the frame and the composer's row | Import `term`. It gets the composer's rendered view in `Frame` |
| `composer` | The prompt input (`composer.Composer`): the draft, its cursor and selection, word wrap, height, and the view and cursor the shell draws | Import `term`, lipgloss, or another uah package, or do I/O. Keys come in as `composer.Key{Name, Text}`; ctrl+v and ctrl+shift+c return an `Action` that the shell carries out |
| `term` | The terminal layer: `Msg`, `Cmd`, `Batch`, `Tick`, `Exec`, the key, mouse, and paste messages, `Run`, which runs a `term.Model`, and `Screen`, the line renderer | Import another uah package. Only `term/uv.go` imports ultraviolet, for its input decoder |
| `bubble` | The TUI's `term.Model`: maps keys to intents, runs effects as `term.Cmd`s, batches session events, owns the composer, and draws frames with `render` | Hold UI state of its own beyond the composer, the window size, and the open session |

When the program ends, `bubble.Run` returns an `Exit` (the open session, its token totals, and the theme; `bubble/exit.go`), and `cmd/uah` prints Codex's exit summary from it: the token usage, `Queued messages kept in the session: N` when messages were still queued (the session keeps them in its sidecar, and resuming it shows them as `↳ queued:` again, unsent until the next message or enter on the empty composer; see [sessions](../session/README.md#messages-queue-steer-interrupt)), and "To continue this session, run:" with `uah resume <id>` on its own line, only for a session that ran. On a terminal it uses the TUI's theme: labels dim and the command in the accent; otherwise, or with `NO_COLOR`, plain text. Because `state`, `render`, and `composer` have no terminal code, the move from Bubble Tea to `term` changed only `bubble`, by a rename of its types. `cmd/uah/tui.go` builds `bubble.Deps` (how to open a session, list sessions, count activity, store pasted images, read the clipboard's image and text and copy text to it, read the plan's usage, and read a session's prompt cache accounting) and calls `bubble.Run`.

**The composer** replaced bubbles/textarea (v2.2.1) and keeps what uah relied on: textarea's default key map (`composer.DefaultKeyMap`), with shift+enter and ctrl+j for a new line; rows that break at spaces as textarea's do, with the last row keeping a cell for the cursor; growth to the height limit, then scrolling to keep the cursor in view; the prompt drawn per visual row, so the λ scrolls away with the draft's first row; the placeholder, word wrapped, on the empty composer's one row; paste with its lines kept and tabs as four spaces; and the 10,000-line cap (`composer.MaxLines`). `Line` and `Column` count lines and runes, and `LineInfo` places the cursor in its wrapped line, as textarea's did. It departs from textarea where textarea was wrong:

- Widths are the renderer's (`ansi.GraphemeWidth`), and the cursor, the deletions, and the wrap step over a grapheme cluster as one (an emoji sequence, a flag, a letter and its combining marks). A wide character never straddles the row's edge.
- ↓ moves one visual row, also into a line's empty last row, and ↑ and ↓ never skip a row one cell wide. A new line is refused at 10,000 lines, as a paste is cut there.
- ctrl+w keeps a space before the word it deletes, and delete at a character no longer also joins the next line.
- `\r\n` in a paste is one line break, not two.
- The composer has no width cap (textarea stopped at 500 columns).

Parity with textarea was checked at 1eafda3, before the bubbles dependency went: the same random keys on both, 3,000 sequences with the draft, the cursor, the height, and the rows equal.

## The terminal layer

`term` runs the TUI's model on the terminal. It replaced Bubble Tea v2 after 1.8.4 ([TUI design](../../docs/design/tui.md#framework-revised-our-own-terminal-layer) has why and the measurements); the model's code did not change beyond the names of its types.

**Types** (`term/msg.go`, `key.go`, `mouse.go`). A model has `Init() Cmd`, `Update(Msg) (Model, Cmd)`, and `View() View`. A `Cmd` is a `func() Msg` run in a goroutine of its own; `Batch` runs several, `Tick` sends a message after a delay, `Quit` ends the program, `SetClipboard` copies with OSC 52, and `Exec` runs a program (ctrl+g's editor) with the terminal released. A `View` is the screen's lines joined by `\n`, the cursor (its place, shape, blink, and colour, or nil to hide it), whether the mouse is reported, and the window title. Input arrives as `KeyPressMsg`, `PasteMsg`, the mouse messages, `WindowSizeMsg`, `BackgroundColorMsg`, and `KeyboardEnhancementsMsg`. Keys keep the fields (`Code`, `Mod`, `Text`) and the names (`"enter"`, `"shift+enter"`, `"ctrl+c"`) Bubble Tea gave them, since both come from ultraviolet's decoder; `term/uv.go`, the only file that imports ultraviolet, turns its events into term's.

**The loop** (`term/program.go`). One goroutine owns the model. It waits on the decoded input, SIGWINCH, the commands' results, the stop signals, and one one-shot frame timer, then takes whatever else is already waiting before it draws, so a paste, a wheel spin, or a batch of session events costs one frame. `View` runs once per frame, not after every update. A change after a pause is drawn at once, so a key echoes without waiting for a tick; changes that come faster are drawn at most `term.FrameRate` (30) times a second, on the one timer. While nothing changes the loop blocks with no timer at all: the idle TUI does not wake up (`idle/tui` in [the perf harness](../../tools/perf/README.md): about 2 to 4 wakeups a second, the Go runtime's, where Bubble Tea's ticker made 165).

**The renderer** (`term/screen.go`). `Screen` remembers each row the terminal shows and writes only the rows that changed. A changed row is written from its first changed cell when everything before it is text every terminal counts as one cell per character (ASCII, Latin, Greek, Cyrillic, punctuation, arrows, box drawing, braille); otherwise the whole row is erased and written. Autowrap is off, so no width is measured to keep a line on its row: a line a terminal counts wider stays on its row, and the erase before each write leaves nothing behind one it counts narrower. A line wider than the row by uah's own count is cut to it, so it cannot overwrite the last column; a line of no more bytes than the row has cells is never measured. When the rows moved up or down (a transcript growing at the bottom, a scroll), the terminal moves them in a scroll region (DECSTBM with SU or SD), and only the rows that came in are written. A frame is one write, inside synchronized output (mode 2026) when the terminal says it has it, with the cursor hidden until it is placed. A frame costs about 2 to 3 µs, where Bubble Tea's renderer, which parsed the whole screen back into cells, took 450 to 590 on the same frames (`go test -run '^$' -bench ScreenFrame ./internal/tui/term`).

**The terminal** (`term/terminal.go`). `Run` puts the terminal in raw mode and the alt screen, turns autowrap off, bracketed paste and modifyOtherKeys on, pushes the kitty keyboard flags, and asks for the kitty flags (`KeyboardEnhancementsMsg`, the new-line hint), the background colour (`BackgroundColorMsg`, the theme), and mode 2026 (not in Apple's Terminal or over ssh, as Bubble Tea did not). The mouse (1002 and 1006), the title, and the cursor's shape and colour follow the view. Colours are downsampled below true colour, and with `NO_COLOR`, through colorprofile; on a dumb terminal, or without `TERM`, the colours go but the cursor moves stay. Leaving resets everything in the reverse order and restores the terminal's mode: on a quit, when the context ends, on SIGTERM, SIGHUP, or SIGINT, and on a panic in `Update`, `View`, or a command, which `Run` raises again after the terminal is restored. `Exec` stops the input reader, drops the keys still queued (typed before the program opened), leaves the terminal, runs the program on it, enters again, and redraws the whole screen at the size it has then. ctrl+c in the program's cooked mode also sends uah a SIGINT, which is dropped while the program runs and for a second after (in raw mode ctrl+c is a key, so a SIGINT otherwise comes from `kill`); `cmd/uah` runs the TUI and its dependencies outside its own signal context, so only `term` decides. SIGTERM or SIGHUP while the program runs ends `Run` at once: the program's context (`term.ExecContext`, which ctrl+g's editor takes for `exec.CommandContext`) ends, which kills it, and the terminal is put back in its first mode. A program that fails is its callback's error; a terminal that cannot be released or taken back ends `Run` with the error, after restoring what it can. The input reader stops even with its queue full, so quitting with keys queued does not hang; a terminal whose input ends without a SIGHUP ends `Run`, after the keys read before the end; a frame that fails to write is drawn whole a frame later, however long it took, and three in a row end `Run`. With `Options.Width` and `Height` set, `Run` is headless on any reader and writer, as `tools/perf` and the tests run it.

## How a message and an effect flow

A key press:

1. `bubble.onKey` maps the key to an intent, such as `state.Submit{Text}` for enter. The approval overlay, the picker, and an open ctrl+r search have their own key maps (`onApprovalKey`, `onPickerKey`, `onSearchKey`), the agent's questions take their keys first and leave the rest to the composer (`questionIntent`), and an open menu takes tab, enter, ↑/↓, and esc first (`menuIntent`).
2. `Model.dispatch` calls `state.Reduce`, which returns the new state and a list of effects, such as `EffSubmit{Text}`.
3. `Model.run` (`bubble/effects.go`) turns each effect into a `term.Cmd` that calls the session (`Submit`, `SteerNow`, `SteerQueued`, `RunShell`, `Interrupt`, `Resolve`, `CompactWith`, `Clear`, `Rewind`, `SetSettings`) or a dependency (`Deps.Sessions`, `Deps.Activity`) off the update loop.
   `term` runs each command in its own goroutine, so the commands that call the session (or the viewed agent, or close the session on a switch or `/quit`) are chained in the order `Update` made them (`bubble/calls.go`): each waits until the one before it has returned. Without the chain, two tab presses could reach `Session.Send` in either order, and the session queues, shows, and sends messages in the order they arrive. `RunShell` and `/review` stay out of the chain, since they return only when the command or the review ends.
4. An effect that produces data returns it as a message, such as `state.ContextShown`. `Model.Update` routes these message types back to `dispatch`, so the reducer handles them like any other input.

A session event:

1. `onOpened` starts a goroutine that groups `session.Events()` into 16 ms batches, so a burst costs one update and one frame.
2. Each batch arrives as one `eventsMsg`. `Update` reduces every event in order and runs the effects they return (a finished run reads the plan's usage), starts the tick if the batch left something moving, then waits for the next batch; exactly one wait is pending at a time, which keeps order.
3. Each session gets a generation number. Batches from a closed session are drained and dropped.

A streamed answer changes with each batch, so it costs at most one render of its markdown per frame, at most 30 a second (`term.FrameRate`). `term` draws only after a change, so the idle TUI does not wake up, and a key after a pause echoes at once ([the terminal layer](#the-terminal-layer)).

A frame: `View` calls `render.Screen`. The transcript is virtualized: it renders items from the bottom up until the window is full. Each item's lines are cached by key, version, width, and view; items that change with time (a running tool, a pending turn) are drawn fresh each frame. A 100 ms tick runs only while something moves on screen: a run, a status, a subagent, a `!` command, or a `/review`. The state's clock is `Deps.Now`, set on each tick and before each key or paste, so a first esc or ctrl+c after the screen sat still is timed from the key, and a test can drive the clock.

Effects made before the first session opens (the startup prompt, for example) are held and run once it opens.

## Transcript items

The transcript is a list of `Item`s, each with a stable key. The reducer updates an item in place by key and raises its `Version`, so a tool call that finishes after later turns updates its original row.

| Kind | Key | Made from |
| --- | --- | --- |
| `KindUser` | `msg:<input ID>` | `InputSent`, or the runner's `UserMessage`; `Raw` keeps the message as sent, with its image tags. `engine.Rewound` removes it and everything after it |
| `KindRun` | `run:<run ID>` | `RunStarted`, updated by `RunFinished` |
| `KindTurn` | `turn:<run ID>:<n>` | `TurnStarted`, updated by `ModelResponded` |
| `KindTool` | `call:<call ID>`; `web:<item ID>` for a web search | `ToolCalled`, `ToolStarted`, `ToolFinished`; `engine.PatchApplied` puts an `apply_patch` call's diff in `Diff` (`state/patch.go`). The call's line is shaped when it arrives (`state/toolcalls.go`): a Bash call's whole command in `Command` and its summary in `Verb` and `Parts`, an MCP call's server, tool, and arguments in `Parts`, and a skill after another joins its `Group` (`MergedInto`, undone when it fails). `engine.ToolOutput` puts why a command or an MCP call failed in `ErrorLine` and an MCP result's summary in `Result`, and `engine.AutoReviewed` puts an approval in `Note` of the latest call with that command. `engine.WebSearch` makes a `web_search` line: running while the provider searches, then done with `searched: <query>`, `opened: <url>`, or `searched: '<pattern>' in <url>` and the detail `hosted` (`state/websearch.go`, the [web search design](../../docs/design/web-search.md)). A `request_user_input` call reads `ASK` with its one question or the headers of several, and `engine.QuestionsAnswered` puts the answers in `Answers`, a line per question (`Migration: Rename in place`; `state/questions.go`) |
| `KindAssistant`, `KindReasoning` | `text:<n>`, `reason:<n>`; `stream:<n>` when streamed | `AssistantMessage`, `ReasoningSummary`; while the model writes them, `engine.TextDelta` and `engine.ReasoningDelta` (below) |
| `KindNotice` | `notice:<n>`; `msg:<ID>` for a message of uah's | Session notices, hook results, command output, approvals; a subagent's notification, the review handed to the agent, and the [prepared context](../contextprep/README.md) a new session starts with ("uah prepared the session's context (3.1 KB)"), each in place of the message that carries it (`state/runevents.go`). The prepared context is a developer message (`core.DeveloperMessage`), or a user message in a session from before the developer role; another developer message is "uah sent the model context (N KB)" |
| `KindAgent` | `agent:<ID>` | `engine.AgentUpdated` (a subagent): `Name` is the nickname, `Text` the ID, `Detail` the state, and `Agent` the latest update (spawn call ID and message, model, effort, why it failed); its tool calls from `engine.AgentActivity` go into `Sub`, drawn under it in the detailed view. `State.Agents` lists them in start order without walking the transcript |
| `KindContext` | `context:<n>` | `/context` (`ContextShown`) |
| `KindFinish` | `done:<run ID>` | `RunFinished`: the end of a run in the compact view |
| `KindMCP` | `mcp:<n>` | `/mcp` (`MCPListed`): one line per server; `Final` asks for the verbose form (`render/mcp.go`) |
| `KindShell` | `msg:<command ID>` | A command you ran in shell mode: `session.ShellStarted`, `ShellOutput` (streamed into `Detail`), and `ShellFinished`; the runner's echo of its record marks it delivered, and a saved record makes it in a resumed transcript (`state/shell.go`, `render/shell.go`) |
| `KindDiff` | `diff:<n>` | `/diff` (`DiffShown`): the work tree's changes in `GitDiff`, drawn with the edit tool's diff renderer under a `DIFF` line (`render/review.go`) |
| `KindReview` | `review:<ID>` | `/review`: `session.ReviewStarted`, `ReviewActivity` (the reviewer's latest tool call), and `ReviewFinished` (its findings) in `Review` (`state/review.go`, `render/review.go`). The message that hands the review to the agent shows as a notice |

The compact view draws one line per tool call, as Codex does; the detailed view (ctrl+t) adds the header, run dividers, turns, and token totals. `LevelDebug` notices show only in the detailed view.

The answer streams on the embedded engine (`state/stream.go`, the [streaming design](../../docs/design/streaming.md)). Each delta appends to a `KindAssistant` or `KindReasoning` item marked `Streaming`, one per model item (and summary part), which draws like a final message. The runner's `AssistantMessage` then replaces the oldest streamed answer in place, and each `ReasoningSummary` the oldest streamed summary part, so the recorded text wins. `engine.StreamReset` (a retry, a failed or canceled request) and the run's end drop streamed items no final message claimed. `State.Writing` reports an answer in progress, for the working line.

## Keys

| Key | Action |
| --- | --- |
| enter | Send. While the agent works, send after the next tool call (`EffSteer` with `session.SendAfterTool`, `Session.Send`): while a model response or tool call is under way the session holds the message, shown as `↳ after tool:` where a tab-queued one shows `↳ queued:` (`state.Queued.AfterTool`, from `session.InputQueued.AfterTool`, cleared at `core.RunFinished` as the session drops the hold; ↑ takes it back), and then gives it to the running agent, so it rides the next model request and never cuts off a response; if the run ends first, it goes out with the next run. **Send keys, as Codex binds them** (`state/sendkeys.go`; the [keys design](../../docs/design/keys.md) has the research and the measurements). `State.SendIntent` maps enter, tab, ctrl+enter, and alt+enter to `Steer` (with its `session.When`: enter `SendAfterTool`, ctrl+enter and alt+enter `SendNow`) or `Submit` (tab, and every key while idle) by whether the agent the composer talks to works (`State.Working`: in the agent view, the viewed agent). The keys are the same in every terminal. Only the hints follow the terminal: `term` asks for key disambiguation at startup, a terminal that answers (kitty, Ghostty) sends `term.KeyboardEnhancementsMsg`, which the shell passes on as `state.KeyboardReported`, and `State.Keys` names shift+enter and ctrl+enter; one that does not answer (tmux in any `extended-keys` mode, Terminal.app) keeps ctrl+j and alt+enter. The compact footer shows `enter after tool · ^enter now · tab later` (or `alt+enter now`) in place of `/ commands` while the agent works and, in the detailed view while idle, `enter send · ctrl+j new line` (or `shift+enter`); the queue says `enter sends now`, and `/help` describes the keys and the new-line key for this terminal.

**The agent's questions**, Codex's `request_user_input` (`state/questions.go`, `render/questions.go`; the [questions design](../../docs/design/questions.md) has the research, checked against Codex `main` at b741e48, and the decisions). `session.QuestionsAsked` adds a `Questions` to `State.Questions`, and the first one shows as a panel above the composer, after an approval if one waits: the headers as tabs, the shown question, its options numbered with their descriptions and notes, and `Type your own answer`. While it shows, `questionIntent` takes ↑/↓ and ctrl+p/ctrl+n (`QuestionMove`), enter, ctrl+enter, and alt+enter (`QuestionAnswer` with the draft), tab and shift+tab (`QuestionSwitch`), and esc, or ctrl+c on an empty composer (`QuestionDismiss`). What else a key does depends on `Questions.Typing`. On an option, a digit picks (`QuestionPick`, which answers at once; the last number takes the own-answer row), `n` starts a note on the option (`QuestionNote`, `Questions.Noting`), and every other key does nothing. While a note is written or the own-answer row is chosen, keys type into the composer, `!`, `/`, and `@` included, with no shell mode or menu: enter keeps the note (`Questions.Notes`) or answers with the composer's words (`Questions.Own`), esc drops the note or interrupts, and leaving the row or the question keeps its words and puts the next one's in the composer. The last answer returns `EffAnswerQuestions` with Codex's encoding (`Questions.Answers`: the label and its note, or `None of the above` and the user's words, each note as `user_note: <text>`) and empties the composer; the shell calls `Session.AnswerQuestions`. Options with a `preview` show the chosen one's in a frame of its own beside the list (each option's description under it) when the panel's body is at least 96 columns wide, else under it, cut to 14 lines with `… N more lines` (`previewBox`, `sideBySide` in `render/questions.go`). `session.QuestionsAnswered`, answered or canceled, closes the panel. The composer's placeholder says what typing does, and the footer drops the send keys' hint.

**Shell mode**, after Codex's and Claude Code's `!`: the composer's λ becomes an accent `!`, the placeholder and the footer's hint say so, and the menu stays closed, so `/bin/ls` is a path. Enter (or ctrl+enter) runs the line as a command in the workspace (`EffShell`, `Session.RunShell`) and returns the composer to messages; backspace on the empty composer, or esc, leaves shell mode first. The command runs at once, also while the agent works; its output streams into a `KindShell` item, drawn on the band after `!` with its exit status and its output folded to 10 rows (50 in the detailed view). Its record goes to the agent with your next message. `State.Shell` holds the mode, `render.ShellPrompt` draws the mark, and `bubble` only maps `!` and backspace and applies the prompt after each reduce. The research and decisions are in the [shell mode design](../../docs/design/shell-mode.md).

**Going back to an earlier message**, as Codex's backtrack (`state/backtrack.go`): while the session is idle with nothing queued, esc on an empty composer primes it ("esc again to edit a previous message"), and a second esc within 2 seconds, or `/rewind`, selects your latest delivered message. The renderer marks it `▶ … ↵ edit from here`, scrolls it a third of the way down the window, and draws the rest of the transcript in the theme's dim color, also what the cut would drop (`render/backtrack.go`). Fading is a pass over the window's lines each frame: it keeps backgrounds, such as the band, and turns every other color and weight to the dim, so the cache keeps each item's own lines and entering or leaving the selection draws no item again. Esc, ↑, and ← select an earlier message; ↓ and → a later one; ctrl+c cancels, and any other key cancels and then does what it does. Enter returns `EffRewind` and puts the message, with its images (`Item.Raw` keeps its image tags), in the composer; the shell calls `Session.Rewind`. When `engine.Rewound` arrives, the reducer drops the message and every item after it, and the footer's meter takes the cut's tokens; a resumed transcript applies the same event after the run it followed. Since it needs an idle session, no streaming item exists when the cut happens. The [rewind design](../../docs/design/rewind.md) has the research and the decisions.

**Selecting text**, as a terminal selects it, while the TUI reports the mouse (`[tui] mouse`, on by default; the [selection design](../../docs/design/selection.md) has the research and the decisions). A press and a drag on the transcript select from cell to cell, a double click selects a word (a run of non-space), and a triple click a line; letting go copies the text and the footer says `copied 3 lines`. Positions are an item's key, a line of its drawing, and a cell (`state.TextPos`), not screen rows, so a selection stays on its text while the transcript scrolls or streams. Dragging to the transcript's top row, or below it, scrolls a line per move, and the wheel keeps scrolling during a drag, with the selection following the text under the mouse. Esc clears the selection and does nothing else; a click elsewhere, typing, sending, and ctrl+t clear it too. The composer and the panels take no selection, nor do the picker and the agent view.

- **State** (`state/selection.go`): `MousePress` (with the line's text and the time, which count the clicks), `MouseDrag`, `MouseRelease`, and `ClearSelection` make `State.Selection`; the release returns `EffCopySelection`, and `Copied` shows the notice for two seconds.
- **Render** (`render/selection.go`): each frame records the transcript line every window row shows, so `Cache.At` turns a screen cell into a position and `Cache.Edge` tells a drag past the top or bottom. The selection is drawn as a pass over the window's lines, as going back fades them: the selected cells lose their styles and take the theme's `Selection` background, so the cache keeps each item's own lines. `SelectedText` (`render/copytext.go`) copies what is drawn, cut by cells (a wide character half inside counts whole), minus decoration: the item's gutter (the λ or ! column and the indent under it, the answer's • column, reasoning's `~`, a warning's mark), the indent each block of lines shares (a code block's or a table's padding), a code block's language, and a quote's `“ ”` marks; trailing spaces and blank lines at either end go.
- **Shell** (`bubble/mouse.go`): maps the mouse to the intents and runs the copy: OSC 52 (`term.SetClipboard`), which the terminal handles, also over ssh, and `Deps.CopyText`, the system's tool (`internal/images/clipboard.TextWriter`: pbcopy, wl-copy, or xclip; none is fine), off the update loop.

**Prompt history**, as Codex's (`state/history.go`, `state/historysearch.go`; the [prompt history design](../../docs/design/prompt-history.md) has the research and the decisions). At startup the shell reads `<uah home>/history.jsonl` (`EffLoadPrompts`, `internal/history`) and the reducer keeps its prompts, oldest first, then this process's (`PromptsLoaded`), each with its workspace. ↑, ↓, and ctrl+r see only the prompts whose workspace is the session's; a line with no workspace is in no view. `SessionOpened` in another workspace rebuilds the view, so `/resume` into another folder shows that folder's prompts, and a prompt sent before the first session opened is written when it opens, with its ID and workspace. Before reducing a `Submit` or `Steer`, `Reduce` records it (`remember`): this process's entry keeps the images' tags, and the file gets `EffRecordPrompt` with the session's workspace and the text as shown, `!` before a shell command, never a slash command; a repeat of this process's last prompt is one entry. `DraftCleared`, ctrl+c on a draft, records it in the process only. `State.Recalls(draft, atEdge, newer)`, Codex's `should_handle_navigation`, tells the shell whether ↑ or ↓ recalls: always on an empty composer, on a recalled prompt left as it was with the cursor at its start or end (`Model.atEdge`), and ↓ only while browsing; otherwise the key keeps its meaning. A recall returns `EffSetDraft`; a `!` entry puts the composer in shell mode, a message gets its images back, and the menu stays closed on a recalled `/model …`. Ctrl+r opens the search (`SearchOpen`), and the footer becomes ` reverse-i-search: <query>` (`render/history.go`) with the terminal's cursor after the query; while it is open every key goes to `bubble.onSearchKey`: text, a paste, backspace, and ctrl+u edit the query, and each edit shows the newest prompt that contains it, ignoring case; ctrl+r and ↑ go to older matches, ctrl+s and ↓ to newer ones, one per text, staying at either end; enter keeps a match as the draft and ↑ goes on from it; esc and ctrl+c put the draft back, with its shell mode and images. The shell appends through a `history.Recorder`, so prompts reach the file in order, and a failed read or append is an error notice.

**Editing the draft in an editor** (ctrl+g; the [editor design](../../docs/design/editor.md) has the research and the decisions). `EditDraft` returns `EffEditDraft` with the draft; the shell runs it as a `term.Exec` (`bubble/editor.go`), so `term` gives the terminal to the editor, alt screen, mouse, and bracketed paste off, and takes it back after, redrawn at the size the terminal has then. The editor command is split into words as a shell would (`mvdan.cc/sh`), so `code --wait` and `nvim -f` work. The result comes back as `DraftEdited`: the reducer makes `\r\n` into `\n`, strips one trailing newline, drops the images whose placeholder is gone (as `DraftChanged` does), and sets the draft; with an error (a non-zero exit, an editor that does not start) it keeps the draft and says so. As Codex does, the shell first checks the session's sandbox policy (the mode and workspace from the state, `Deps.WritableRoots` from `cmd/uah`) and refuses, keeping the draft, when sandboxed commands could write `<uah home>/editor`: never for `~/.uah`, whose `.uah` stays read-only in every writable root, but for a `$UAH_HOME` in the workspace, `/tmp`, or a writable root; full access has no sandbox. `Deps.Exec` stands in for `term.Exec` in tests.

In the picker, ↑/↓ choose, enter resumes, tab switches between this directory and all directories, typing filters, and esc goes back.

In the `/config` panel, ↑/↓ choose a setting, enter or space changes it, ←/→ cycle back and forth, and esc closes; while a value is being typed, enter saves it and esc cancels (see [/config](#config)).

In the `/model` picker, ↑/↓ (or ctrl+p/ctrl+n) choose, enter on a model lists its efforts and enter on an effort applies both, esc on the efforts goes back to the models, and esc (or ctrl+c) on the models closes it (see [Slash commands](#slash-commands)).

## Slash commands

`state.Commands()` is the registry; `/help` prints it in this order. A command without "While busy" waits until the agent is idle. A message is a command only when its first word after `/` is letters, digits, `-`, and `_` (`commandLine`); a draft that starts with a pasted path, such as `/Users/me/a.json - take this json`, is sent as a message.

`/model` offers the provider's model list after a space: the first `/model` draft loads it through an effect (`EffLoadModels`, `state/models.go`), off the update loop, from the catalog in `internal/models`. When that list came from the provider, `/model` refuses a model it lacks with the nearest names; with no list, or only the bundled one, any model passes.

`/model` asks for the effort right after the model, as Codex's model popup opens its reasoning popup (checked against Codex rust-v0.159.1). Enter on `/model` in the command menu, or `/model` sent with no argument, opens the picker above the composer (`ModelPicker`, `state/modelpicker.go`); tab still completes `/model ` for an argument (`Command.Bare`). The picker lists the provider's visible models in priority order with the current one selected and marked; without a loaded list it shows `loading models…` until `ModelsLoaded` arrives, and a provider that lists nothing closes it with a notice to use `/model <id> [effort]`, as does a shell without `Deps.Models`, which answers `EffLoadModels` with an empty list (`bubble/effects.go`). Enter on a model lists the levels its catalog entry accepts, lowest first, with the default marked `(default)` and each level's description when the provider gives one (`models.Model.ReasoningHelp`); a model without levels in the list gets every level uah knows. As in Codex, the current model's effort is preselected on the current model, and the model's default on another; a model with a single level applies at once. Enter on a level sends one `EffSetSettings` with both, the same path `/model` and `/effort` take, so the session changes live on the embedded engine and the `SettingsChanged` notice says when it applies. esc on the efforts goes back to the models with the chosen one selected, as esc pops Codex's reasoning popup back to the model list. Codex's enter also saves the model and effort as defaults (its `s` key applies to the session only); uah's picker applies to the session only, and `/config` saves them. `/model <id>` checks the model as before and opens the picker at its efforts, waiting for the list when it is not loaded; `/model <id> <effort>` skips the picker and refuses a level the model does not list.

`/diff` and `/review` follow Codex's commands (see the [review design](../../docs/design/review.md)). `EffDiff` collects the changes with `internal/gitdiff` off the update loop (`bubble/review.go`), and `DiffShown` brings them back. After `/review ` the menu offers Codex's presets (`state/reviewmenu.go`); `/review branch ` and `/review commit ` list the local branches and the newest 100 commits, read once per review (`EffLoadReviewTargets`, `ReviewTargetsLoaded`). A complete target returns `EffReview`, which calls `Session.Review`; the session's review events draw the item, and esc esc stops the review as it stops a run. One review runs at a time, and the findings reach the agent with the next message.

MCP prompts (`state/mcp.go`) join the commands: "/" starting a draft loads them through `EffLoadMCPPrompts` (`bubble/mcp.go`, from `Session.MCP`), the menu lists them after the built-in commands with their arguments and description, and `/help` lists them last. A command that is not built in but names a prompt becomes `EffRunPrompt`: the shell gets the prompt (`mcp.Manager.GetPrompt`), turns its messages into one message (`mcp.PromptText`, images attached), and submits it as typed text is submitted.

`/model`, `/effort`, `/fast`, and `/adaptive` apply from the next model request, or from the next run when the run just stopped; the session's `SettingsChanged` event says which. `/fast` needs a provider with priority processing (`Session.Priority`, kept in `State.Priority`); on another it says so.

## /config

`/config` opens a panel above the composer, after Claude Code's `/config`: the basic settings, one row each, with the value a session opened now would use and where it comes from, as `uah config` explains them (`app.Explain`). The selected row is in the accent band; the title names the user file changes go to.

| Row | Key | Change | Applies |
| --- | --- | --- | --- |
| Auto-compact | `auto_compact_percent` | Cycles off, 50, 60, 70, 80, 85, 90, 95% | New sessions |
| Auto-compact token limit | `model_auto_compact_token_limit` | Type a number; empty or 0 removes it | New sessions |
| Compaction model | `compact_model` | Cycles the session's model and the provider's models; the session's model removes the key | New sessions |
| Model | `model` | Cycles the provider's models, or type one when there is no list | This session too, as `/model` |
| Effort | `effort` | Cycles low to max | This session too, as `/effort` |
| Fast mode | `fast` | Toggles | This session too, as `/fast`, where the engine has it |
| Adaptive effort | `adaptive_effort` | Cycles off, 1 step, and 2 steps; while selected, the panel says what it does ([engine README](../engine/README.md#adaptive-effort)) | This session too, as `/adaptive` |
| Permission mode | `permission_mode` | Cycles read only, workspace, auto, as shift+tab does without `--yolo`; yolo is never saved | This session too, as shift+tab |
| Web search | `web_search` | Cycles live and disabled | New sessions |
| Details view | `[tui] details` | Toggles | At once |
| Mouse | `[tui] mouse` | Toggles | At once |

The split follows the rest of the TUI:

- **State** (`state/config.go`, `state/configrows.go`): `ConfigPanel` holds the loaded values, the selected row, and a value being typed. The reducer turns a change into `EffSaveConfig`, shows the new value at once with the user file as its source, and, for a setting the session takes live, adds the same `EffSetSettings` that `/model`, `/effort`, `/fast`, `/adaptive`, and shift+tab send. Opening the panel loads the values (`EffLoadConfig`) and the model list (`EffLoadModels`).
- **Render** (`render/config.go`): the rows, the value in bold, on in the good color, the source dim, the selected row's help (`ConfigRow.Help`) when it has one, and the keys at the bottom.
- **Effects** (`bubble/effects.go`): `Deps.Config` and `Deps.SaveConfig`, which `cmd/uah` backs with `app.Inspect` and `app.SaveSetting`. A save goes through the comment-preserving editor that `uah mcp add` uses (`internal/config/tomledit`); a change that would stop a session from starting, such as fast mode with a provider that has no priority processing, is undone and reported. After each save the panel reloads, and says so when a flag, the environment, a configuration layer, or a trusted project file still sets the key and wins over the user file ("model still comes from config.d/host.toml, which wins over the user file").

## The agent view

`/agents Ada` (or an ID prefix; the menu completes the nicknames) shows a subagent's transcript in place of the session's, under one header line: `agent Ada · alt+← alt+→ switch agents · esc esc interrupts`. It follows Codex's `/subagents` switch, where the TUI shows another thread of the session and the user can type to it. alt+← and alt+→ step through the main agent and the working subagents in the order they started, wrapping around, as Codex's previous- and next-agent keys do; on an empty composer alt+b and alt+f do the same, since many macOS terminals send those for alt+arrows (`SwitchAgent`). A finished or interrupted subagent is not a stop and `/agents <name>` does not open it: its answer is in the main transcript, where its end shows as a line (`Rex completed; the main agent was told`, from the `<subagent_notification>` the main agent got), and `uah sessions show` prints its run.

- `state.AgentView` holds a second `State` for the agent, reduced from its events by the same reducer and drawn by the same renderer, with a cache of its own. The session's own events keep reducing into the main state meanwhile.
- The shell follows the agent with `Session.WatchAgent` (see [internal/session](../session/README.md)): its earlier runs become a `HistoryLoaded`, then its events arrive in 16 ms batches as `state.AgentEvents`, like the session's.
- A message typed in the view goes to the agent (`EffAgentSend`), as the parent's `send_input` does. `/agents` and `/quit` work as usual; enter, ctrl+enter, and tab reach the viewed agent's live run after its next tool call, now, or after the run (`EffAgentSend.When`), as they do the main agent's, and on an empty composer sends the agent's own queued messages now (`EffAgentSteerQueued`). Other commands are for the main agent and say so. esc esc interrupts the viewed agent while it works (`EffAgentInterrupt`, which stops its own subagents too), as it does the main agent; alt+← back to the main agent, or opening another agent, ends the view. The clock keeps ticking while any subagent runs, so their spinners move while the main agent is idle.
- An approval or the agent's questions waiting in the session show the session's screen until they are answered.

Blank lines between items come from `transcriptLines` (`render/backtrack.go`): an item gets a blank line above it when it or the item above it stands apart (`apart`: your message, and a tool call drawn on more than one line, such as an edit with its diff or a call with a second line) and neither already has one there, so calls of one line stay together. The blank line is part of the item's lines, so the backtrack fade, text selection, and the scroll count it with the item, and a copy drops it when the copy already ends with a blank line. The banner loses its own blank line when the first item starts with one, so there is never more than one blank line in a row. The [tool calls design](../../docs/design/tool-calls.md) records the choice.

Markdown goes through `render/markdown`: goldmark parses it with the GFM extensions, and its own renderer walks the tree. Each `Styles` owns one `markdown.Renderer`, which keeps the finished top-level blocks of the messages it drew and the highlighted code, so a message that grows (a streaming answer) re-renders only its last block, and a width change renders once more at the new width. The [Markdown design](../../docs/design/markdown.md) has the reasons and the numbers.

A `Theme` holds every color: the accent, dim text, the notices' gray, the band, the breath's shades, the code colors, the diff tints (Codex's dark tints in `Amber`, GitHub's light ones in `AmberLight`), which diff code blocks share, the selection's background, and the colors `/context` tells its categories apart with, which also color GitHub alerts' titles. `Amber` is for dark terminals and `AmberLight` for light ones. `term` asks the terminal for its background at start (`term.BackgroundColorMsg`); `ThemeFor` picks the theme and tints the band from that background, as Codex tints its message background, and the shell makes a new render cache for it (`NewCache(theme)`). The cache holds the theme's `Styles`, and every drawing function is a method of `Styles`, so there is no shared styling state: two caches draw two themes side by side, and render tests can run in parallel. A new theme is a new `Theme` value. Text is never colored by the theme, so it keeps the terminal's own foreground, except while going back, when everything but the selected message is dim.

## Images

The composer takes images as Codex's does; the [images design](../../docs/design/images.md) has the research and the reasons.

1. ctrl+v or alt+v (`PasteImage`) runs `EffPasteImage`: the shell reads the clipboard through `Deps.Clipboard` (`internal/images/clipboard`: osascript on macOS, wl-paste or xclip on Linux) and stores the image through `Deps.Images` (`internal/images.Store`), off the update loop. A clipboard without an image pastes its text into the composer (`Deps.PasteText`: `clipboard.TextReader`, which runs pbpaste, wl-paste, or xclip).
2. A bracketed paste that is one image file's path (quoted, shell-escaped, `file://`, or `~/`), which is also what a terminal pastes for a dropped file, becomes `AttachFile`; choosing an image file after `@` does the same in place of its path (`acceptImage`); an MCP resource after `@` never does, whatever its URI ends with.
3. `ImageAttached` adds the image to `State.Attached` with the next label, and `EffInsertText` puts `[Image #N] ` at the cursor. `ImageFailed` shows a warning and pastes the text it came from.
4. `DraftChanged`, and a draft edited with ctrl+g (`DraftEdited`), drops the images whose placeholder is gone. Backspace at the end of a placeholder first deletes the rest of it (`eatPlaceholder`), so one key removes it. A number is not reused while its image is attached, and numbers are not renumbered.
5. Submit and steer join the draft's images to the message as tag lines (`images.Join`). The transcript, the queue, and a resumed session show the text without them (`images.Display`), and ↑ takes a queued message back with its images (`DraftRestored`).
6. An image in an MCP resource the message names, or in an MCP prompt's result, is stored the same way and joined after the message's own images with the next free label (`bubble/mcp.go`).

## Plan usage

The ChatGPT plan's usage (see [internal/usage](../usage/README.md)) shows in four places. `cmd/uah` passes the session's reader in `Deps.Usage`; without one, the TUI has no usage, as for a provider without it.

| Place | Shows | Read |
| --- | --- | --- |
| `/status` | A notice with the plan and a row per window: `weekly [███████████████░░░░░] 78% left (resets 15:44 on 26 Sep)`. When the read fails, the error and the last snapshot, marked `stale` after 15 minutes. For another provider, "usage is not available for <provider>" | On each `/status` (max age 0) |
| Footer | The tightest window before the context meter: `weekly 78% left · 64% context left`. Hidden before the first read and for a provider without usage | After each run (`RunFinished`), cached 60 s |
| Warnings | "Heads up, you have less than 25% of your weekly limit left (resets …)", once per window when it passes 75, 90, and 95% used; a window that resets warns again | The read after each run |
| Limit reached | "Usage limit reached; try again at 15:44 on 26 Sep.", once per run, when a `RunnerError` or a model failure is the usage limit (`usage.LimitReachedIn`). The time comes from the failure text when it kept it, else from a fresh read; without one, the notice links ChatGPT's usage page | On that failure (max age 0) |

The state holds `State.Usage`: the last snapshot, whether the provider has none, and the thresholds already warned. The reducer asks for a read with `EffLoadUsage{Reason, MaxAge}`, from `usageAfter` (which `Reduce` calls for each session event) and from `/status`. `bubble/usage.go` calls the reader off the update loop, and the answer comes back as `UsageLoaded`, which `onUsage` handles by its reason. There is no timer.

`/usage` and `/status` also show the open session's prompt cache in one line, read from its recorded runs (see [the cache accounting](../usage/README.md#session-prompt-cache)):

```text
prompt cache 86% · missed 119k: effort switches 72k, cold start 9k, other 38k · ≈20% of usage (API-price estimate)
```

The share of input served from the cache comes first, then the input that the session could have found cached and did not, by cause, and what that input cost as a share of the session's usage at API prices. A session without misses shows `prompt cache 93% · no misses`. Both commands return `EffLoadCache{SessionID}` (`state/cache.go`, none before the session has an ID). `bubble/usage.go` calls `Deps.Cache` off the update loop, which `cmd/uah` sets to `session.CacheStats`, and the answer comes back as `CacheLoaded`, which `onCache` shows. A failed read is a debug notice. Without `Deps.Cache`, the TUI shows no cache line.

## Extending the TUI

To add a slash command that only changes the view, add an entry to `Commands()` in `state/commands.go` with a `run` function that edits the state and returns no effects. `/details` is an example.

To add a command that needs data from the session, follow `/context`:

1. `state/contextview.go`: define the effect (`EffContext`) and the result message (`ContextShown`), the command function that returns the effect, and the reducer handler (`onContextView`). Call the handler from `Reduce` in `state/reduce.go`.
2. `state/commands.go`: add the command to `Commands()`.
3. `bubble/effects.go`: add a case to `Model.run` that calls the session (`sess.ContextUsage()`) and returns the result message.
4. `bubble/model.go`: add the result type to the list in `Update` that routes messages to `dispatch`. A result type missing from that list reaches the composer's handler (`onComposerMsg`) and is lost.

To add an item kind, follow `KindContext`:

1. `state/items.go`: add the kind and any fields it needs to `Item`.
2. Put items with `State.put` and a key from `nextKey`, or a stable key when later events update the item.
3. `render/items.go`: add a case to `itemLines`, and to `compactLines` when the compact view draws it differently. Put larger drawing code in its own file, as `render/contextview.go` does.
4. If the item changes with time, return true from `Item.Live`, so the cache does not serve a stale frame.

To add a key, map it to an intent in `bubble/keys.go` and handle the intent in `state.Reduce`. Keep the existing keys' meanings.
