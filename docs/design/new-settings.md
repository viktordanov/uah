# New settings after an update

Status: explored and built 2026-11-27 on `feat/advisor`, for the release after v1.17.2. Ledger item 160. Codex facts are from rust-v0.172.0's source; Claude Code facts are from its 2.1.332 binary.

A feature that is off until configured, such as the [advisor](advisor.md), stays unknown to the people who update: uah never adds a setting to their `config.toml`, and the examples are in `docs/configuration.md`, which a release install does not carry. The owner's idea (2026-11-27): update the configuration safely with the new options, commented out, and point people to it.

## How Codex and Claude Code do it

- **Codex** (rust-v0.172.0, `codex-rs/config/src/types.rs`) keeps a `[notice]` table in the user's own `config.toml`: whether a warning or a model migration prompt was acknowledged (`hide_full_access_warning`, `hide_gpt5_1_migration_prompt`, `model_migrations`). It writes that table itself (`codex-rs/core/src/config/edit.rs`), so it does edit the user's file, but only to record what was shown, one notice at a time.
- **Claude Code** (2.1.332) keeps `lastReleaseNotesSeen` in `~/.claude.json`. At startup, `computeUpdateSummary` compares it with its own version and shows the release notes between the two (`startup_update_summary`); the value here was its own version after that start.

Both record what they showed: Codex by flags in the user's file, Claude Code by a version in its own state file.

## Options

| Option | For | Against | Taken |
| --- | --- | --- | --- |
| Edit the user file at every start, adding new tables commented out | Nothing to run; the file always shows the options | The file is the user's: a dotfiles checkout, a symlink, or a file another tool writes changes under them unasked; every user gets new startup behavior in an otherwise ready release | No |
| `uah config update`: the same block, on request | The owner's idea, with consent; comments only, so any uah, an older one too, reads the file as before | The user has to run it | Yes |
| A one-time notice in the first TUI session after an update | Tells people the setting exists and what to run or ask | One more line under the welcome box, once | Yes |
| The built-in `uah-customization` skill describes each new setting | Asking the agent works after an update, with no network | Only helps when someone asks | Yes (ledger rule 8) |
| A reference file of every key, rewritten at each start | Every option in one place | A second source of truth beside `docs/configuration.md`, about 150 keys to write and keep in step | No |
| Release notes at startup, as Claude Code shows | Covers more than settings | uah has no changelog to show; a bigger change | No |

## As built

- **The keys.** `config.Keys()` walks the `Config` struct's TOML tags, nested tables and maps included (`mcp_servers.<name>.command`). The reference test checks that `docs/configuration.md` names each.
- **The record.** `~/.uah/settings-seen` lists the keys the user has seen named (`config.Unseen`): a header line, then a comment line per key, so the record is TOML with nothing in it, and a configuration path that names it by mistake sets nothing. A file there without the header, with a line that is not a comment (a setting someone saved there), or a symlink there is not uah's: uah leaves it alone and names nothing. The unseen keys are those of this version that the record lacks; the record then holds them all. Keys, not versions: a source build (`dev`, a pseudo-version, `+dirty`) and a release that share a home would otherwise name the same setting twice or never.
- **Upgraders from v1.17.2.** v1.17.2 and earlier keep no record, so a home without one that was used before (the user file exists, or the state directory, or the home when the state is elsewhere, has `sessions/` or `uah.db`, checked before the session creates them) compares with v1.17.2's keys, frozen in `internal/config/newsettings/keys-v1.17.2.txt`. A new home has seen every key and hears nothing.
- **The settings.** `config.NewSettings` describes each top-level table a release adds (a block at the end of the file keeps only a new table's keys in scope once uncommented; a key added to an existing table would need another kind of notice): the keys it introduces, a summary, a question for the agent, its anchor in `docs/configuration.md`, and examples that load as a user file. `TestNewSettingsCoverNewKeys` fails for a key that is new since v1.17.2 and that no entry lists, a later key under an announced table too, so a feature cannot add a setting without saying how to use it. The claude -p example is checked against the reference's.
- **The notice.** The TUI's first session of a process shows one line per new setting, as information (`session.Options.Infos`, `LevelInfo`), not a warning: what it does, that `uah config update` adds it to the user file, commented out, and what to ask the agent. `uah exec`, `uah review`, and subagents neither show nor record it, so a script cannot use it up. The TUI records the keys once a session has opened (`Unseen` returns `record`, `pendingSettings` holds it): each session it opens names them until one opens, so a session that fails to open, or a resume whose history does not load, leaves them for the next. The record is read and written under a lock (`settings-seen.lock`, `flock`), and a write keeps the keys another session wrote since. It appends the lines the record lacks through the file it read and checked, first finishing a header or a line a crash cut short, and replaces nothing, so an edit another program made stays; a record cut short is still uah's if it starts with `# uah:`, and names again at most the keys it lost; an empty file there is not uah's. A missing record is written whole beside it and hard-linked into place, or, where the file system has no hard links, created exclusively; a symlink there is not followed; two TUIs that start at once may both name the settings. A record that cannot be locked or read names nothing, rather than the same settings at every start. The command it suggests always names the file by its absolute path (made absolute without cleaning, as a `..` after a symlink is the link's), quoted for a shell, since `--config`, `UAH_CONFIG`, `UAH_HOME`, or `HOME` may have picked it for the session's command only; a path that needs quoting gets no command, as bash, fish (a backslash in single quotes), and PowerShell (no `'\''`) each quote their own way. `Open` sizes its event buffer for its notices and infos, so it never waits for a reader.
- **`uah config update`** (`config.AddNewSettings`) appends each new setting that the user file neither sets nor has the whole block of, as comments between a marker line (`# uah config update: [advisor], added commented out`) and an end line (`# uah config update: [advisor] ends`), which it looks for, so it adds a block once and again after an append that stopped partway. It reads the file first, so one that needs nothing, read-only too, is only read; to append, it opens the file once more, without blocking, checks that descriptor is a regular file, and holds an `flock` on it from the read to the append, so runs that overlap add one block; after the append it checks that the path still names that file, since an editor that saved by a rename left the block in the old one. An empty `--config` is an error, not a fallback to `UAH_CONFIG`. Not covered: a `/config` or `uah mcp add` save in another uah that read the file before the append and renames over it after; `tomledit.Write` takes no lock, and the block is lost until the next run. It finds a table the file sets in any case, as the loader matches it (`[Advisor]`), and a marker only as a comment line, not as text in a string, found in one scan with the editor's parser (`tomledit.CommentLines`), after a BOM too. A file that is not valid TOML is left alone, and so is anything but a regular file, such as a device; a missing file is created. It appends and rewrites nothing: a save that replaces the file meanwhile stays (and is reported; an editor that writes in place at that very moment is not covered), a symlinked file stays a link (a link to a file that does not exist yet creates that file, and the folder a chain of links leads to, resolved as written, so a `..` after a linked folder is resolved where it leads), the file keeps its permissions, and since every line it adds is a comment, a reader that comes in between still reads valid TOML. `tomledit.Write`, which replaces a file and its link, is not used: following links there would let `uah mcp add`'s write to a project's file reach outside the project. `update`'s own `--config` names the file, else `UAH_CONFIG` or the default, as every subcommand reads its own; a different `--config` on `uah` or `uah config` is refused (`updateTarget`), not ignored, judged from the parsed flags, since reading the command line again mistook a prompt's text for a flag. An empty `UAH_CONFIG` counts as unset, for every command (`nonEmptyEnv`), so a session reads the file the notice names. `--dry-run` prints the blocks. Each block links the reference at this uah's release tag, a prerelease's too, or its commit for a source build (golang.org/x/mod's pseudo-version parsing), else `main` (`docsRef`). In a file with only comments, `tomledit` puts a new root key before the first block (`rootInsert`), not at the end, where uncommenting the block's table would take it: `/config`'s `effort` would turn into the advisor's. `tomledit.CutTables` ends the last table where such a block begins, so `uah mcp remove` of the last server keeps the examples. A `settings-seen` that is not a regular file, such as a FIFO, is refused, not waited on, and one over 1 MiB is not read; a record that fails to be written goes to the TUI's log and the next session tries again; and a file there that is not uah's record, a user's file that happens to be at that path, is never written over. A key of the last table that a user put below an update block is cut with the table.
- **Checked.** In a temporary home with `sessions/` and no record, the TUI named `[advisor]` under the welcome box and wrote the record; the next start named nothing; a new home named nothing.

## Open

Decisions with the default taken (ledger rule 7):

1. **Startup edits:** none. If people do not run `uah config update`, an opt-in setting could let uah add the blocks itself; default no.
2. **Where the notice shows:** the TUI only. `uah doctor` could list the settings the user file does not set; default no.
3. **A full reference file:** not built; `docs/configuration.md` stays the reference.
4. **When the notice counts as seen:** once `session.Open` returns, a moment before the TUI draws it. A TUI that exits in that moment leaves the settings recorded but not seen; moving the record into the TUI's handling of the notice would close it. Default: as built.
